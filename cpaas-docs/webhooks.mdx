This section covers the webhook capabilities currently documented for **SMS and RCS** in GTS CPaaS+.

Webhooks let CPaaS+ send event notifications to an application endpoint when supported events occur. They provide an event-driven alternative to repeatedly polling an API for updates.

Choose the relevant channel guide below for its configuration details, event types, payload fields, and callback-handling guidance. SMS and RCS have different documented setup details and payload structures.

## How the callback flow works

1. **Configure a callback destination.** Provide the application endpoint that should receive notifications, following the setup instructions for the channel.
2. **Subscribe to supported events.** Enable the event subscription relevant to the notifications your application needs.
3. **Receive the callback.** CPaaS+ sends an HTTP request containing the event data to the configured endpoint.
4. **Process the event.** Read the channel-specific payload and update your application using the identifiers and status fields provided.

The exact configuration options, event names, payload fields, and callback behavior are channel-specific. Refer to the channel guide rather than assuming that SMS and RCS use identical settings or payloads.

## Implementation considerations

- **Use a reachable endpoint.** Make sure your application endpoint is available to receive inbound HTTP callbacks.
- **Handle requests promptly.** For SMS DLR callbacks, the documented guidance is to return **HTTP 200 OK** promptly. A non-200 response or timeout may result in retries.
- **Validate and protect the endpoint.** Apply the authentication and network controls documented for the channel. The SMS DLR guide specifies Bearer Token authentication and lists the GTS callback source IP for firewall allowlisting. Do not assume those details apply to other channels unless their documentation confirms it.
- **Design for repeated notifications.** Where retries may occur, make event processing safe to repeat. Use the identifiers available in the payload to help detect events your application has already processed.
- **Keep an operational record.** Log callback receipt time, event type, relevant message identifiers, processing outcome, and errors without unnecessarily storing sensitive message content.
